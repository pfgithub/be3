1. Add the block (if the block type is new)

- crates/block-client/src/blocks/foo.rs — state struct, operation enum, impl Block with a fresh TYPE_ID UUID, #[cfg(test)] mod tests;.
- crates/block-client/src/blocks.rs — add foo::Foo; to the block_types! list (alphabetical), with : Default when the new-block menu can make one from its default.
- crates/block-client/src/blocks/foo/tests.rs + one file per test under tests/ (serialization round trip, operation edge cases).
- A block holds what it is, not what an editor makes of it. The image block keeps the file's bytes and a metadata field saying what decoding them found — or why it failed — which the editor fills in through an operation the first time it draws the image. Nothing but the plugin then needs a decoder, and no other client has to decode the block to know its shape.

2. Create the plugin package

- crates/editors/foo/Cargo.toml — copy checklist's: crate-type = ["cdylib", "rlib"], deps block-client, block-editor-plugin, uuid. The package name is the wasm artifact stem, so a multi-word editor uses underscores (workspace_index). It also has to be a name no crate the workspace depends on already has, so the image editor's package is image_block; the display name in the manifest is what the user sees.
- crates/editors/foo/src/lib.rs — block_editor_plugin::plugin!(app::FooApp, "../manifest.json");
- crates/editors/foo/src/app.rs — impl block_editor_plugin::App: connect stores client.get_block(block_id), then ui, toolbar_ui, left_sidebar_ui, right_sidebar_ui, preview_ui reading through block.read() and writing through block.operate(...). Local-only view state lives in the struct. An instance is drawn by one egui context, whatever it is showing: the frame it is edited in and the preview the host paints its block on are separate viewports of that one context, so a texture is uploaded once and used by both rather than kept per screen. block_editor_plugin installs the Material icon font into every plugin context and re-exports egui_material_icons, so icons come from block_editor_plugin::egui_material_icons::icons rather than a dependency of the package.
- crates/editors/foo/manifest.json — the plugin's identity and everything the host is told about it (see below).
- Root Cargo.toml — add "crates/editors/foo" to members.

The client every connect is handed is the plugin runtime's one block client, shared as an Arc by every instance it opens: the creation dialog, the editor that follows it, and any artifact instance all speak to the server through it. Keep the Arc for as long as the instance needs it, and expect blocks another instance already opened to be the same live blocks. Because the client belongs to the runtime rather than to an instance, work an instance started - a block it has just created - still reaches the server after that instance closes. The client has no connection of its own: its frames are tunnelled through the host's, which carries them every frame for as long as the runtime lives, whether or not anything is drawing the plugin. Nothing about that is the plugin's business, but it is why a plugin that draws nothing still gets its work saved.

What connect's EditorHost offers, for anything the plugin cannot do itself:

- open_block(id, block_type) — opens another block in a tab of its own.
- block_types() — the host's registered block types, for naming and illustrating a block this editor only holds a reference to. Pass it to block_ui::BlockLabel (re-exported as block_editor_plugin::block_ui) so labels match the rest of the app, including how an automatic name is italicized.
- editable() — whether the block this instance was opened on may be edited, so an editor does not write back what it worked out (an image's decoded size) on behalf of a reader. The host cannot disable a plugin's own surface the way it greys out an editor it draws itself, so an editor whose block may only be read keeps every gesture that would change it behind this: the pixel art editor still pans, zooms and reads out pixels, but draws nothing and disables the buttons that would.
- drag() — the block the app is dragging over the screen being drawn, in that screen's own coordinates, and whether it has been let go. Draw the drop feedback yourself and answer accept_drag(bool), which decides the cursor the host shows.
- pick_file(filter) — the host's own file picker, the only one that works on desktop, Android and the browser alike. block_editor_plugin::FilePicker wraps it the way the app's own picker works: open(&host, filter), is_open(), and poll(&host) until it answers.
- fetch(url) — a GET the host makes on the plugin's behalf, answered with take_fetch(request) once the body arrives or the attempt fails. A plugin has no network of its own on any platform, so this is the only way it reaches one, and the host refuses any URL whose host name the manifest's network list does not name. The paint review editor downloads its snapshots this way.
- pick_block(filter) — the host's own block picker, which is how an editor acquires a child without waiting for one to be dragged in. The filter names what is being chosen, the block types that may be chosen, empty for any, and whether the picker opens on the templates the host offers rather than on its new-block grid. block_editor_plugin::BlockPicker wraps it the same way FilePicker wraps the file one, and answers with the block the user chose or created.
- child(ui, block_id, block_type) — embeds another block's editor where the ui is (see below). child_sized takes the size to give it rather than the space the ui has left, which is what a list of thumbnails wants.
- present(on) and presenting() — asks the host to give this instance the whole window with no chrome bands and show nothing else of the app, and reports what the host settled on. The host owns the answer: it takes presenting away when the user presses Escape or the instance stops being the one on screen, so an editor reads presenting() rather than remembering what it asked for, and draws its content the same way either way.
- show_band(band, shown) — hides one of the chrome bands the manifest declares, for a sidebar that has nothing in it at the moment. The band is laid out by the framework either way; this only says whether to call the editor for it.
- occlude(rect) — declares that the editor draws over that rectangle after the children placed so far, so the host neither draws nor routes input to them there.
- set_creation_ready(bool) — whether a creation dialog has been filled in, which is what lets the user accept it (see below).

An editor never lays out its own frame. The framework hands it the frame it was given, puts the toolbar row, the sidebars and the content where crates/block-ui decides they go, and calls toolbar_ui, left_sidebar_ui, right_sidebar_ui and ui into them. It draws the breadcrumb and the way back out itself, so an editor cannot lose it, and it clips each band so an editor cannot paint outside the one it is in. Which bands an instance is given changes from frame to frame and an editor is not told which: the same code draws a tab of its own, a block being edited inside a canvas, and a slide inside a deck.

App::intrinsic_size reports the size the editor wants wherever the host embeds it (a canvas, a text block). App::aspect_ratio reports the shape of the block, which the host holds a preview to. Leave either unimplemented to take the host's default.

Drawing the block itself: an editor that lists Preview among its regions is asked to draw its block wherever the host paints it rather than opening it — a canvas entity, a slide, a block embedded in text. The host maps that screen onto the quad it is painting, straight from the plugin's surface, so preview_ui fills the screen it is given and lets the host place, rotate and fade it. It has no background of its own, so whatever is behind the block shows through. A frame is the same: it is transparent wherever the editor does not paint, which is what lets the layer beneath show through around a block being edited inside a canvas. Children placed in a preview work like children anywhere else, so an editor whose block is only its children - a presentation showing its first slide - draws them there as previews.

Embedding other editors: host.child(ui, block_id, block_type) takes the space the ui has left and puts that block's editor there, whatever draws it — another plugin, an editor the app draws itself, several levels deep. The child is drawn *under* the plugin's own surface and the space it takes is cut out of it, so anything the editor draws after the child — a selection handle, a drag ghost, a menu, a modal — covers it simply by being drawn later, and rounding the hole with set_corner_radius keeps the editor's own background around the child's corners. A child that is genuinely translucent cannot composite that way and is placed with child_above instead, which composites against the plugin's pixels and cannot be drawn over.

The handle it answers with carries the child's own response, so the editor keeps every click over a passive child: nothing is delivered to the child until the editor promotes it with activate(), which is what a double-click or an Edit button does, and the host takes the promotion away again when the user clicks outside or presses Escape. A child that is not something the user promoted but the whole of what the editor shows - the slide a presentation is editing - is placed with keep_active() instead, which is live from the moment it is placed and which the host never takes away. set_mode(ChildMode::Preview) asks for the other end of that: the host draws the block rather than running its editor, which is what a filmstrip of thumbnails wants. A preview child is composited over the plugin like any other child below it: the host draws the block's own preview into the hole, clipped to where the child was placed. None of that is the editor's to arrange: place the child, ask for Preview, and draw the rest around it. Ask the handle what the host made of the child: available() is false when the block cannot be opened — a block already open above this editor is refused, and error() says so — while intrinsic_size(), aspect_ratio(), hovered() and active() are what the host last saw. Place only the children that are visible: the host runs a bounded number of them as editors and draws the rest as previews.

A child the user has promoted with activate(), or one the editor placed with keep_active(), takes the frame over: it is handed the same frame this instance was, draws every chrome band in it, and draws its content at the rectangle it was placed at. The editor that placed it is told for that frame that its chrome is only reserved: its bands keep exactly the geometry they had and it paints nothing in them, so its content does not move and a canvas keeps its zoom and its pan to the pixel. There is no way to nest a child's chrome inside a band of your own, and no way to keep a band while a child has the frame - a deck whose slide is being edited has to put what it wants on screen in its own content area, beside the stage rather than around it. The user leaves the child with Escape or the exit the framework draws, and the host hands the frame back.

Making a new block: the plugin makes every block of its type, so an editor the new-block menu offers implements connect_creation and create_block whatever its creation mode. The host opens an instance with a client of its own but no block, and create_block makes the block through that client and answers with its id or with why it could not be made. Create it orphaned and leave it that way: the host adds the reference and sets the parent once it has the id, and then opens the block, so one plugin runtime serves the creation and the editor that follows it. The host closes the creation instance as soon as it has the id, and the runtime's client carries the creation to the server after that, so create_block does not have to wait for the block to arrive. The host is the one that waits: a block only exists for the server once the plugin's client has said so, so the parent the host then sets is held back until the server has told it the block is there.

Artifacts the editor generates: a block type that produces dynamic artifacts — a PNG exported from a drawing — lists ArtifactSettings among its regions, which is what tells the host this plugin answers for the artifacts its blocks make. The editor creates one through its own client with create_dynamic_artifact, putting whatever it needs in the descriptor's opaque payload, and asks the host to open it. The host then keeps a second instance of the plugin open for as long as that artifact is on screen and asks it, through connect_artifact, describe_artifact, artifact_settings_ui, regenerate_artifact and poll_artifact, which block the payload was generated from and what it currently produces, how to edit it inside the host's settings dialog, and how to rebuild the artifact. The host owns the settings it has stored and hands them over whenever they change; the settings screen edits a copy of them, which the host only stores once the user applies it, and throws away when the dialog is dismissed. Regeneration writes the artifact block through the instance's own client, so it polls like any other work waiting on a block to load (see below).

An editor whose block cannot exist until the user has chosen something (the file behind an image) sets "creation": "Dialog" and also implements creation_ui, which draws inside the host's shared dialog frame; set_creation_ready(true) tells the host the dialog may be accepted, and create_block is called on acceptance. An "Immediate" editor is asked for its block as soon as the instance is open, and the host shows only a spinner while it starts.

3. Write the manifest

manifest.json is the plugin's single source of truth: the plugin reads its own identity out of it and the host reads everything else. Nothing in block-app is touched to add a plugin.

```json
{
  "id": "be3.foo",
  "name": "Foo",
  "version": "0.1.0",
  "block_type": "00000000-0000-0000-0000-000000000000",
  "display_name": "Foo",
  "icon": "\ue3f4",
  "creation": "Immediate",
  "regions": ["Frame"],
  "chrome": ["Toolbar"],
  "entry_point": "foo.wasm",
  "network": []
}
```

block_type is the uuid of a block type block-client declares — a plugin cannot bring a block type of its own, which is what keeps child operations, history and duplication working. icon is a codepoint of the app's Material font, not a name to look up. Entry points name a file beside the manifest, which is where cargo already put the plugin, so nothing a plugin was compiled to is moved to be found.

The entry point is the wasm module the build leaves beside the manifest: one artifact, the same bytes on the desktop, on Android and in the browser. network is the host names the plugin may reach through host.fetch, matched whole against the host of an https URL, and empty for a plugin that reaches nothing.

regions says which kinds of screen the host may give an instance: Frame, which every editor has and which is the whole rectangle it is edited in, Preview, and ArtifactSettings. chrome says which of the toolbar row and the two sidebars this editor offers inside its frame; the plugin reads that list out of its own manifest and the framework calls only the bands it names. creation is Immediate for a block a user can make from the new-block menu with nothing to fill in first, Dialog for one the editor has to ask about first, or None for one only another block ever produces. The optional fields default to the plainest answer: children says which of the host's structural edits the block type accepts, important puts it in the main section of the add-block picker, interaction says whether an embedded instance is live or only previewed until it is focused, capabilities carries rotation, aspect ratio and pan-and-zoom, and resize says how an embedded instance may be resized.

A cursor an editor sets while drawing — ui.ctx().set_cursor_icon(...) — is passed to the host, which shows it while the pointer is over that screen, so a canvas can offer a crosshair or a grabbing hand without knowing anything about the window it is in.

capabilities.pan_and_zoom means the editor's content has a view of its own rather than simply filling the space it is drawn in: the host works out where inside the editor's own content band the content goes, against the band the editor reported laying out last frame. The host owns that view. It hands the rectangle over as host.view(), in the coordinates the editor is drawing in, and the editor draws its content there at the resolution it is being shown at, keeping no zoom or offset of its own; an instance never told where its view is fills the content it is given instead. The editor moves the view by asking - host.pan_view(delta), host.zoom_view(factor, anchor) and host.fit_view() - which is what a zoom or fit control in its toolbar calls (the pixel art editor puts a zoom readout, zoom buttons and a fit button in its own). The host answers against whatever it is showing the instance in, so those controls work the same in a tab of the editor's own as inside an infinite canvas the block sits in, where zooming zooms the canvas and the block's content grows with it; the editor cannot tell the difference, and its zoom readout is true either way as long as it works it out from the rectangle it was given. Wheel, pinch and middle- or space-drag over the content belong to the host as well, so an editor leaves them alone; a gesture only that editor knows about - the PDF editor panning on a plain drag - it turns into a request of its own.

A manifest is untrusted input, so a bad one is skipped and reported in the Plugins debug window rather than crashing the app.

The host discovers plugins beside its own executable, from the <plugin id>.plugin.json manifests the build leaves there next to the modules cargo produced. The browser and Android cannot list a directory, so they read the same manifests through a plugins.json index instead, from the bundle root and from the assets root. Every platform runs the same host: plugin_host/runtime.rs owns the runtimes, the instances they show, input, errors and restarting, and a platform only implements its Backend - starting a runtime, exchanging messages with it, and handing over the frame it drew. There are two: plugin_host/wasm.rs runs the module under wasmtime on every platform but the browser, and plugin_host/web.rs runs the same module in a worker in the browser. A plugin runs beside the app rather than inside it either way: a thread of its own under wasmtime, a worker of its own in the browser. Neither side polls the other. Everything a plugin says arrives on its own, in the order it said it, and wakes the host; everything the host says reaches the plugin the same way.

4. Extending the protocol

If the editor needs something the host has and the plugin does not, add it to crates/block-plugin-api (a Message or EditorMessage variant, plus validate coverage and a round-trip test), accept it in the plugin's ClientSession state machine, route it in crates/block-app/src/plugin_host/instances.rs, and surface it on EditorHost or App. A message a plugin sends reaches the host by itself as long as it is not one of the session's own - the handshake, acknowledgements, errors, ping and shutdown - which Message::is_session names. Bump PROTOCOL_VERSION and describe the new rule in crates/block-plugin-api/PROTOCOL.md. Anything the host and a plugin both draw — labels, shared painting helpers — belongs in crates/block-ui, which both depend on.

5. Work that does not finish in one frame

A plugin runtime draws only when the host asks it for a frame; it paces none of that itself. When the host tells it something that changes what it shows, or something wakes it, it says a frame is needed and waits, so a burst of input or view changes it cannot keep up with is drawn as one frame carrying all of it rather than one frame each. The frame it last drew says how long it wants to wait before being drawn again, which the host holds until it comes due and then answers with a single request at the start of its own frame, so an editor animating without pause is drawn once per host frame instead of as fast as its process can run, and one the host is not drawing on screen is asked for nothing until it is on screen again. That request leaves before the host lays anything out, carrying the frame's input with it - routed against where the editor sat and what covered it the last time it was drawn - and input the host routes always brings a request with it, since input is a change the editor will want to show. The host takes whatever the runtime has published by the time it has finished building its own frame, so an editor that answers while the host is still laying out is shown in the frame that asked rather than the one after it. A message that changes nothing it draws - a client frame on its way to its own block client, an acknowledgement - costs no frame; the client wakes the runtime itself once it has something new to show. The host repaints on the same rule: a message that changes nothing it draws does not schedule a frame, and nothing about a plugin is polled. An editor doing work off the frame — the PDF editor renders its pages on a thread of its own — asks to be drawn again through ui.ctx().request_repaint() or request_repaint_after(...), which reaches the runtime's loop wherever the request came from; block_editor_plugin::Waker, which host.waker() hands out, does the same for work that has no ui to ask from. Work that is a future rather than a thread - block-client's own version control routines, which await the blocks they touch - is started with host.spawn(future), which answers with a Task the editor polls with take() and asks finished() about, and which wakes the runtime itself when it completes. The future runs wherever the platform runs futures: a thread of its own on the desktop, the runtime's own task pump inside the wasm guest, which is why it never needs an executor of the plugin's own. An idle editor that asks for nothing costs nothing.

A plugin is one wasm for every platform, so a dependency it cannot have there is a dependency it cannot have at all: nothing that reaches the network (host.fetch instead), nothing that opens a file, and nothing wasm-bindgen. A dependency that only exists on some targets belongs behind a [target.'cfg(...)'.dependencies] table with a stand-in module for the rest, the way the PDF editor keeps PDFium out of its wasm build. std::thread works — the host implements thread spawning against the plugin's own shared memory — but only the plugin's first thread may talk to the GPU, and a call from any other is refused by name. A native library the plugin loads at runtime is looked for beside the app, since the app, the server and every plugin share one directory.

6. Build scripts

Nothing to edit: ./scripts/build scans crates/editors/*/manifest.json for every target and copies each manifest beside what cargo produced as <plugin id>.plugin.json. Plugins are built by a cargo call of their own, for wasm32-wasip1-threads with the plugin profile, because the app links wgpu with real backends while a guest links it with only the custom one and one call would unify the two. ./scripts/build --target TRIPLE --release --output DIRECTORY packages the app, the server and every plugin for a cross target, which is the one place the artifacts are copied.

7. Verification

Run ./scripts/verify, which builds the app and every editor's tests for the host but not the plugin wasm, then ./scripts/build --target web, which builds the browser's half of the bootstrap and every plugin as the guest it actually ships as. A plugin can be driven without a GUI: cargo run --example instantiate -p block-wasm-host -- target/wasm32-wasip1-threads/plugin/foo.wasm takes it through the handshake, opens an instance, asks for a frame and fails unless it presented a surface.

A plugin never learns where its pixels live. It asks for a render target and is handed an opaque texture, which under wasmtime is a texture the app already owns in its own device — nothing is exported or imported — and in the browser is the swapchain texture of the worker's own offscreen canvas, which the host then copies from on the GPU. Its wgpu calls reach that device over the ABI in crates/block-gpu-abi, implemented for the guest by block-gpu-guest against wgpu's custom backend, and answered by block-gpu-host, which wasmtime drives directly and the browser drives through crates/block-gpu-shim, a wasm-bindgen module the worker instantiates first and binds the plugin's imports to.
